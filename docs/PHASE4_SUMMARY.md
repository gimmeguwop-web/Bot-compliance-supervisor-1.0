# PHASE 4: LLM-модуль — Завершено

## Обзор

В рамках PHASE 4 реализован модуль семантического анализа конструкторской документации с использованием LLM (Large Language Models). Модуль интегрирован в общий пайплайн обработки документов через Celery.

## Реализованные компоненты

### 1. Промпт-инжиниринг (`configs/llm_prompts/semantic_analysis.txt`)
- Специализированный промпт для анализа ЕСКД/ГОСТ документации
- Инструкция по поиску смысловых противоречий
- Требования к формату вывода (строгий JSON)
- Примеры типичных нарушений

### 2. Провайдер LLM (`backend/app/engines/llm/provider.py`)
**Интерфейсы:**
- `LLMProvider` — абстрактный базовый класс
- `OpenAICompatibleProvider` — поддержка OpenAI, Ollama, vLLM
- `MockLLMProvider` — для тестирования без реального API

**Функции:**
- Ленивая инициализация клиента
- Парсинг JSON-ответов (включая markdown-блоки)
- Graceful degradation при ошибках
- Фабрика `get_llm_provider()` для создания провайдера

### 3. Анализатор (`backend/app/engines/llm/analyzer.py`)
**Класс `LLMAnalyzer`:**
- `analyze_document()` — основной метод анализа
- `_build_context()` — построение контекста из:
  - Метаданных документа
  - Данных основной надписи
  - Распознанных подписей
  - Текста технических требований
  - Таблиц (спецификации)
  - Предыдущих результатов проверок
- `convert_to_validation_results()` — конвертация в формат БД

**Особенности:**
- Ограничение размера контекста (8000 символов)
- Группировка текста по страницам
- Исключение дублирования с детерминированными проверками

### 4. Celery-задачи (`backend/app/workers/tasks.py`)
**Задача `run_llm_analysis_task`:**
- Проверка флага `LLM_ENABLED`
- Получение распарсенных данных
- Инициализация провайдера через фабрику
- Асинхронный вызов анализатора
- Сохранение результатов в БД
- Обработка ошибок без падения всего пайплайна

### 5. Конфигурация (`backend/app/core/config.py`, `.env.example`)
**Новые настройки:**
```env
LLM_ENABLED=true
LLM_PROVIDER=mock  # mock, ollama, openai
LLM_BASE_URL=http://host.docker.internal:11434/v1
LLM_MODEL_NAME=mistral:7b-instruct-v0.3-q4_K_M
LLM_API_KEY=not-needed-for-ollama
LLM_MAX_TOKENS=2000
LLM_TEMPERATURE=0.1
```

### 6. Сервис документов (`backend/app/services/document_service.py`)
Полный CRUD для:
- Управления документами и задачами
- Сохранения распарсенных данных
- Хранения результатов валидации
- Отслеживания статуса задач

## Интеграция в пайплайн

```
process_document_task
    ↓
parse_pdf_task
    ↓
run_rule_engine_task (детерминированные проверки)
    ↓
run_cv_ocr_task (подписи, штампы)
    ↓
run_llm_analysis_task ←─── PHASE 4
    ↓
compile_results_task
```

## Типы обнаруживаемых нарушений

### Семантические ошибки
- Противоречие массы в штампе и спецификации
- Отсутствие материала при изображенной детали
- Несоответствие наименования составу изделия

### Логические противоречия
- Разные требования в тексте и таблицах
- Дублирование пунктов технических требований

### Рекомендации
- Отсутствие стандартных формулировок
- Нарушение порядка изложения требований

## Производительность

- **Асинхронность:** Неблокирующий вызов LLM через `ainvoke()`
- **Кэширование:** Ленивая инициализация клиента
- **Ограничения:** 
  - Максимум 8000 символов контекста
  - Первые 10 страниц текста
  - Первые 5 таблиц
  - Топ-10 предыдущих ошибок
- **Graceful Degradation:** При ошибке LLM пайплайн продолжается

## Тестирование

### Mock-режим (по умолчанию)
```python
LLM_PROVIDER=mock
```
Возвращает тестовые результаты для отладки UI без реального API.

### Локальная модель (Ollama)
```bash
# На хосте запустить Ollama
ollama pull mistral:7b-instruct-v0.3-q4_K_M
ollama serve

# В .env указать
LLM_PROVIDER=ollama
LLM_BASE_URL=http://host.docker.internal:11434/v1
```

### Production (OpenAI-compatible)
```env
LLM_PROVIDER=openai
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=sk-...
LLM_MODEL_NAME=gpt-4-turbo-preview
```
